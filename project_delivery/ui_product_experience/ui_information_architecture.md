# UI 信息架构：研发变更审查工作台

## 修改前的问题

原界面按项目概览、文档版本、检索、变更、轨迹、评测等技术模块排布。首次访问的用户需要自行推断系统处理什么业务问题，也缺少清晰的起点。变更分析、人工审核和发布在同一长页面中，用户不容易看出任务进度。修改建议和引用依据分散，审核时需要往返查找。

## 修改后的设计

首页以“版本可信研发知识与变更审查系统”为标题，先解释需求变更、影响分析、引用依据、人工审核与安全发布的业务价值。Public Demo 明示所有研发资料均为合成数据。主入口是“开始一次变更审查”：选择 Case A 或 Case B 后进入现有变更分析流程；“开始 Demo”复用同一真实流程，不生成假结果。

首页状态卡片读取现有文档目录与服务状态，显示所选案例的项目、该项目需求文档当前有效版本、目录中的研发文档数和版本数、系统就绪状态。版本由实时目录派生，不能把不同项目的版本硬拼在一起。当前公开语料中，Case A 对应 PAYMENT，Case B 对应 AUDIT；目录总量在本次验证时为 9 份文档、11 个版本。若目录不可用，界面显示“待连接”，不伪造版本。

导航按用户任务重新排序：

1. 工作台：业务定位、实时状态、案例选择和引导。
2. 变更分析：需求差异、影响文档、引用依据。
3. 修改审核：修改前、建议修改、关联依据三栏及现有人工审核操作。
4. 版本发布：现有应用修改、质量门禁、候选版本与安全发布操作。
5. 知识检索：保留可信问答、证据检索与版本差异能力。
6. 执行轨迹：保留任务过程追踪。
7. 评测结果：保留现有评测展示。
8. 扩展工具：保留原文档模板起草入口，作为辅助功能，不置于核心业务路径。

变更分析、修改审核和版本发布页均展示同一条任务状态。状态只由已有的需求差异、影响项、选中依据、修改建议、人工审核、候选版本和任务终态推导；没有新增后端状态或工作流节点。首页用五个业务步骤说明路径，首次访问有可关闭的轻量引导。小屏幕使用双列状态卡片与靠前的快速入口，工作台采用平面浅灰底、深蓝标题和蓝色主按钮。
