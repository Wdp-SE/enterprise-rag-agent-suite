# 秋招面试讲解要点

## 1. 为什么这不是普通 RAG？

普通 RAG 解决“从文档里找内容并回答”，本项目还要解决企业文档会持续演进的问题。检索前先确定项目、文档类型、文档 ID、版本和 ACTIVE 状态，回答后保留可追溯引用；当需求变化时，Agent 还能识别受影响内容、给出局部修改建议并生成候选版本。

## 2. 为什么要做版本治理？

研发知识最危险的问题之一是旧文档仍然能被搜到。系统显式维护 ACTIVE/SUPERSEDED 和版本关系，正式检索只使用当前有效版本，从数据层避免旧需求污染回答，而不是让模型自己猜哪个版本更新。

## 3. Evidence 为什么不等于事实？

Evidence 只是检索到的候选依据。它还需要通过 Scope、版本、新鲜度和引用校验。系统只把校验后的证据交给后续步骤，并在证据不足时明确拒答或要求人工处理。

## 4. 为什么“疑似影响”不能当成事实关系？

显式引用、字段映射等属于已确认关系；依靠语义相似度发现的内容只代表可能相关。界面将两者分开，防止用户把模型建议误认为已经确认的依赖关系。

## 5. 为什么使用局部 Patch，而不是整篇重新生成？

企业文档的大部分内容通常没有变化。局部 Patch 只替换被确认影响的目标片段，能保留模板、格式和未受影响内容，也更容易审计修改前后差异。

## 6. 如何发现并发修改冲突？

执行前会核对基线版本、目标锚点和原始内容摘要。如果文档已经被其他人修改，Gate 返回 `BASE_VERSION_MISMATCH` 或 `TARGET_CHANGED`，阻止在过期上下文上覆盖内容。

## 7. 如何保证幂等性？

每次应用都包含稳定的任务与目标信息。若相同 Patch 已经执行，Gate 返回 `ALREADY_APPLIED`，不会再次修改文档或重复产生候选版本。

## 8. 为什么生成 Candidate，而不是直接替换原文档？

Agent 的建议不能直接成为企业事实。系统先创建候选版本，完成完整性校验并经过人工审核后才激活；原 ACTIVE 文档在候选发布成功前保持不变。

## 9. Checkpoint/Resume 如何避免重复副作用？

工作流把阶段状态、Trace 和已经完成的副作用写入 Checkpoint。恢复时从最后一个安全阶段继续，并结合幂等校验跳过已经完成的应用与发布动作。

## 10. Evidence Context Budget 解决什么问题？

它限制每个字段进入上下文的证据数量，并在截断前完成范围校验、去重和必需证据优先。这样既控制上下文规模，也避免关键依据被相似但重复的片段挤掉；Trace 还能解释每一步剩余多少证据。

## 11. 为什么没有使用 Hybrid Search？

当前语料和评测已经证明 DENSE_ONLY + SECTION_PATH 能稳定满足目标。为了简历项目的可解释性和可维护性，没有为了技术名词堆叠引入 BM25/Hybrid 生产分支。后续只有在固定评测证明关键词召回存在系统性缺口时才会增加。

## 12. 为什么没有使用 LangGraph？

当前工作流阶段有限，现有 Python 状态机已经提供 Trace、Checkpoint、Resume 和确定性测试。引入 LangGraph 会增加依赖和学习成本，却不会改善当前业务指标，所以保留更透明的实现。

## 13. 为什么没有增加 AI Coding 场景？

项目的业务主线是研发文档知识与变更审查。AI Coding 会引入仓库索引、代码执行和更复杂的权限边界，容易稀释当前闭环，因此只作为未来方向，不在本轮实现。

## 14. 未来怎样扩展到 Git Diff？

可把 Git Diff 解析为结构化 Change Event，再复用现有 Scope、Evidence、影响识别、Quality Gate 和人工审核链路。新增的是代码变更适配器和仓库权限控制，现有 RAG 与 Agent 核心边界不需要推倒重来。

## 15. 当前系统有哪些限制？

- 评测语料和案例规模仍然有限，不能代表所有企业文档。
- 影响识别依赖文档结构质量，扫描件和复杂表格仍可能降低效果。
- 真实生产环境还需要统一身份、权限、审计存储和监控。
- 当前离线基线只说明版本过滤的价值，不是线上 A/B 实验。
- 主流程没有可靠的模型 usage 和统一价格来源，因此没有展示估算 Token/成本。
