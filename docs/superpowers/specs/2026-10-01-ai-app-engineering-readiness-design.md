# 研发知识 RAG 与证据约束变更审查：求职导向迭代设计

状态：待用户审阅的架构规格；本文件不表示实现已完成。

## 1. 目标与业务定位

面向研发变更发起人和技术审查人，提供版本范围受控、来源可追溯的研发知识检索与变更影响候选分析。系统把自然语言变更描述整理为受控检索计划，检索相关研发资料，输出可能影响项、证据、版本/语言来源状态和待补查缺口；工程师审核后作出最终决定。系统不自动修改公开上游资料或把语义相关性描述为已确认影响。跨语言同步差异审查只适用于经过确认的对应文档对，不默认比较所有中文和英文资料。

首要任务是变更影响审查；研发工程师的直接资料问答是次要任务。知识库治理、企业身份与长期审计属于后续生产化范围。

## 2. 依据现状与业务边界

当前公开演示使用固定 Autoware 语料，计有 1,148 条版本/语言来源、660 个主题/路径和 7,927 个检索片段。默认 `latest` 是 Documentation `main` 与 Universe `0.52.0` 的组合范围，不是同一软件发行版。260 页社区中文译文中，44 页路径可与当前官方英文资料形成对应候选；路径相同本身不能证明译文完整、语义等价或版本同步，其余 216 页也未核实对应关系。当前语料扩充后仅有 10 条双语冒烟测试，不构成质量基准。目前登记 74 个图像引用，只有 2 张图的文字经过人工复核并进入检索。

因此：
- 公开演示的准确表述是“Autoware 公开研发资料的版本化、多语言检索与变更审查演示”。
- 当前不宣称已经实现企业内部中英文版本漂移检测、全量图片问答或生产级审批审计。
- 社区译文的路径候选、人工校译状态、版本对应状态必须分开记录；路径匹配不能升格为已确认译文对。
- 显示“latest”时说明其具体资料组合，并在每条证据上展示仓库/组件版本；禁止把复合范围静默显示成单一产品版本。
- 本地合成工程资料可用于展示需求、设计、接口、测试等企业式文档关系，必须显式标注合成数据；它与公开语料是同一系统的不同工作区，不是两个项目。

文档关系分为四种状态：`verified_pair`（人工确认属于同一逻辑文档/版本谱系）、`candidate_pair`（路径、标题或内容相似但未核实）、`independent_or_localized`（独立资料或有意本地化版本）、`unknown`（尚未判定）。只有 `verified_pair` 可以触发双语版本差异判定；`candidate_pair` 仅作为待核关系提示；后两种状态继续参与适用范围内的检索，但不作为译文漂移证据。区域化差异只有在区域/变体元数据或明确规则可查时才可解释为有意差异；缺少规则时标记待审核，不静默忽略。当前 44 条路径候选需进一步抽样/人工核验，不能直接计为 44 对已验证译文。

## 3. 用户需求与质量取舍

### 3.1 研发工程师：直接资料问答

目标是快速找到正确版本的依据。关键质量为指定版本正确、答案引用有效、回答完整而简洁。证据不足时保留来源并说明缺口，不以速度为由跳过版本过滤。

### 3.2 变更发起人/技术审查人：主工作流

目标是尽量发现必需的受影响资料并形成可审核候选。相对于直接问答，允许更多检索步骤和较长响应时间，优先保证完整来源召回、版本正确和可追溯。增加候选会造成审查负担，因此需做排序、去重和“明确关系/语义候选/待补资料”区分。关键漏报代价通常高于少量可管理的候选误报。

### 3.3 技术负责人/质量审核人：最终决策

目标是核验建议的依据、范围和不确定性。输出必须能回溯来源、版本和证据缺口；不允许将关键词覆盖率或检索分数标为概率置信度，也不允许 Agent 自动批准或修改资料。

### 3.4 初始时延目标（待实测校准）

- 暖机后纯检索 API P95：初始目标不超过 2 秒。
- 单轮生成问答端到端 P95：初始目标不超过 15 秒。
- 有界变更审查端到端 P95：初始目标 30–45 秒；过程中显示阶段状态，超时后保留已取得证据。
- 以上是首轮验收假设，不是已达到的线上 SLA；需分别测冷启动/暖机、检索、模型和完整任务耗时，并根据托管服务真实数据调整。

## 4. 目标数据与评测设计

保留现有 10 条冒烟集作为接口/语料回归，不把它扩充成唯一评测。新增带版本号、标注规范、数据指纹和运行配置的 Autoware 双语质量集。建议首轮人工标注约 80–120 条，作为工程诊断和策略对比集，不宣传为真实用户分布或统计性行业结论。

覆盖题型：
1. 单文档事实查询；
2. 跨章节及跨来源必需证据；
3. 显式版本限定与错版本干扰；
4. 中文查询命中英文原文；
5. 英文查询命中中文资料；
6. 已对齐与未核验社区译文的对照；
7. 图片独有信息与正文+图片组合问题；
8. 语料确实无答案及超出范围问题。

按文档家族、版本或变更场景划分开发集/留出集，避免同一文档近似问法跨集合泄漏。每条问题记录必需来源、允许版本、答案支持句、语言关系、是否可回答、文档关系状态和图片锚点。双语差异评测只使用人工确认的同谱系文档对；若公开语料里可确认的配对样本不足，可另建明确标记的合成配对样例验证同步差异逻辑，不把它们混入公开语料检索成绩。对困难标注进行人工复核。LLM 评分只用于辅助筛查，关键样本由人工确认。

评测分层报告，不汇总成一个准确率：
- 检索：必需来源 Recall@K、完整必需来源命中、MRR/nDCG、版本正确率/错误版本率。
- 问答：逐声明证据支持率、引用精度与召回、回答完整性、无答案拒答精度/召回。
- Agent：变更分类、查询计划覆盖、影响候选召回与精度、证据缺口识别、每次任务工具调用数。
- 工程：冷/暖 P50/P95、各阶段耗时、模型成功/超时/拒答原因、输入输出 token 与估算费用。

晋级规则：BM25 保留为冻结基线；每次只改变一个策略因素。新策略必须在开发集达到预先定义的目标改进，在留出集证明收益，同时满足显式版本集零错版、无答案错误回答不恶化、引用成员校验不退步和时延预算。策略失败时记录结论并保留基线。

## 5. 目标运行链路

### 5.1 版本化 RAG

1. 验证工作区、资料范围、版本和语言筛选。
2. 对用户查询做可解释的规范化/同义词处理；不得静默改变用户指定版本。
3. 以 BM25 为对照，逐一实验章节语义切块、双语混合检索、RRF 融合和可选重排。
4. 按去重、来源可信度、版本和语言对应状态整理证据。
5. 返回证据锚点、资料版本、语言、来源状态、检索策略和诊断信息。
6. 生成仅使用本次证据的答案；引用成员校验失败、无有效引用或资料不足时拒答并保留证据。

### 5.2 图片证据

建立图像清单，记录源文档/章节、原图 URL 与 SHA、图像类型、OCR/人工复核状态和文字位置。OCR 只产生待复核候选；经人工确认的文字可进入索引。只有查询指向图像时才路由到图片证据，减少普通请求的额外耗时和费用。复杂箭头、颜色、空间关系或安全语义不能从纯 OCR 文本推断；需要视觉模型时先单独基准测试并人工验证。

### 5.3 证据约束 Agent

保留确定性变更分类和有界查询计划，避免直接引入无边界自主循环。每个步骤记录查询、命中的证据 ID、是否纳入结果和缺口。结构化输出包含：
- 变更摘要和适用范围；
- 影响候选、候选类型和关联依据；
- 每条建议对应的证据 ID/来源版本；
- 资料缺口、语言未核验或版本冲突提醒；
- 人工审核动作与审查状态。

明确关系与模型推断关系分开；证据不足时标注待核，不自动写回上游。输出采用结构校验和引用成员校验。调用数、总超时和上下文长度采用服务端硬边界。

### 5.4 结果界面

按任务类型展示：问答模式突出简洁答案和引用；变更审查模式突出影响候选、证据、缺口和审核动作。默认显示用户决策所需的版本、语言和来源关系；请求 ID、模型、耗时等技术诊断放在可展开的技术详情中。把已有规则提示命名为“证据覆盖提示”，不称为答案置信度。

## 6. 工程发布与企业化

### P0：发布可追溯

工作台和 RAG API 应提供构建提交号、语料清单指纹、检索策略版本和生成配置摘要。构建信息由部署流水线或受控构建清单写入，不能依赖未经验证的平台环境变量。部署 Smoke 将预期版本与线上工作台/API 实际版本比对，并检查健康状态、中文/英文检索、版本过滤、无答案、生成失败保留证据等路径。公网版本未与本地候选提交核验前，不标记为已发布。

### P1：运行观测

为每个请求记录 request ID、应用提交号、语料指纹、模型/提示词版本、检索策略、检索数、阶段耗时、状态码、token 用量和安全失败原因。日志不记录密钥、完整提示词或不必要的原始用户资料。可逐步对齐 OpenTelemetry 的 trace/metric/log 语义字段。

### P2：企业真实部署

在接入私有资料前增加登录身份、租户隔离、检索前 ACL/RBAC、持久化审计、资料生命周期状态、长期存储和管理员工作流。公开演示继续使用公开或明确标记的合成资料。无固定单会话次数上限不代表无限安全：公网部署需结合供应商预算告警、防刷、并发和超时保护。

## 7. 分阶段实现边界

1. **发布真实性与基准底座（P0）**：构建身份、在线版本核对、评测数据规范和报告结构。
2. **资料范围及质量评测（P0）**：明确复合 latest、组件版本、译文对应状态；建当前语料分层问题集并固化 BM25 指标。
3. **RAG/图像策略实验（P1）**：按失败分类逐项测章节切块、双语召回、重排、图片 OCR；仅晋级通过门槛的策略。
4. **Agent 和界面验证（P1）**：针对变更审查任务评测计划、证据绑定、候选质量、拒答和时延；重整用户结果层级。
5. **企业化边界（P2）**：先完成威胁/权限/保留策略设计，再逐步实现身份、持久审计与访问控制；外部 Jira/GitHub 工单连接器不作为本轮前置工作。

每阶段需单独可运行、可验收；数据语料和策略变更都更新指纹与评测报告。旧 DolphinScheduler 成绩及扩充前 Autoware 结果仅作历史实验背景。

## 8. 明确不做

- 不直接替换 BM25 为向量检索、Hybrid 或重排，除非当前冻结评测证明收益。
- 不声称当前社区译文已与官方英文完全对齐。
- 不声称全量图片已识别，不从图形 OCR 推导未记录的箭头或空间关系。
- 不展示未校准的百分比置信度。
- 不自动修改、审批或发布上游研发资料。
- 不以新接多个 Agent、MCP、Jira 或行业语料数量替代业务评测。
- 不把演示评测指标描述为线上业务效果或企业生产 SLA。

## 9. 完成定义

- 线上 UI/API 版本和目标提交一致，且可展示语料及策略指纹。
- 新评测可在固定语料上重复运行，指标按任务类别报告，BM25 基线可复现。
- 候选策略按明确门槛晋级或被拒，理由留档。
- Agent 的每条输出候选可回溯证据或显式标记证据不足；人审边界可验证。
- 图片证据状态和双语对应关系不会被 UI 或回答过度表述。
- 文档、接口、测试、README 和面试介绍一致区分“已实现”“已评测”“仍属后续企业化”。
