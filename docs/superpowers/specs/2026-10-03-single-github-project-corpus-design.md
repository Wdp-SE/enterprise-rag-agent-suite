# 单一 GitHub 项目的研发资料 RAG 与变更审查设计

## 1. 目标与业务边界

将当前演示系统定位为：面向工业安全视觉监控应用研发、测试与交付人员的项目级资料检索和变更影响审查工具。系统围绕一个可追溯的 GitHub 应用项目工作：工程师按项目提交版本查询设计、实现、配置、部署和测试资料；发生代码或配置变更时，Agent 根据变更差异和 RAG 证据整理可能受影响的模块、配置、文档与验证项，供工程师审核。

本项目是基于公开开源项目构建的求职演示原型，不代表 Seeed、NVIDIA 或其他公司的内部系统，不声称其公开资料包含真实企业 CR/ECO 流程，也不声称完成生产现场验证。所有自行编写的评测问题和演示变更都明确标为“模拟”，不得伪装成上游真实工单或 PR。

业务场景暂定为 Seeed 官方工业视觉监控指南指向的 `xbs0325/industrial-inspection` 应用，指南描述其在 reComputer Industrial J4012 / JetPack 7.2 上运行，包含 YOLO PPE 检测、VLM 行为告警与 Docker 部署：<https://wiki.seeedstudio.com/industrial_vision_monitoring_on_industrial/>。该仓库由非 Seeed 官方组织维护的可能性较高，因此产品指南中的链接关系不等于仓库由 Seeed 官方发布。仓库归属、内容、固定 commit 和许可仍须独立核实，未核实前不纳入公网正文索引。

## 2. 活动语料与来源准入

### 2.1 单项目来源原则

活动语料以一个固定 GitHub 仓库及其固定 commit 为唯一应用项目来源。设备厂商公开资料仅在直接支撑该应用的硬件、驱动、JetPack、摄像头或部署问题时作为环境参考资料纳入；它们必须标为“项目依赖参考”，不能引入另一应用、另一业务流程或另一套活动工作区。

优先顺序：

1. 应用项目 GitHub 仓库中明确标注许可的内容；
2. Seeed 官方中文文档中直接说明目标 J4012、JetPack、相机或 Docker 运行前提的页面；
3. NVIDIA/JetPack 官方资料中能核验目标版本与运行依赖的部分；
4. 其他来源仅作为链接元数据，除非来源、许可和纳入理由均经人工复核。

“官方”按实际发布者标记：Seeed 官方 Wiki、NVIDIA 官方资料、应用 GitHub 仓库维护者资料不能混写为同一发布方。官方指南引用第三方仓库不自动授予该仓库内容的再分发权。

### 2.2 仓库文件范围

在许可允许的前提下，完整盘点并尽量纳入能够支持研发查询和变更审查的仓库材料：

- `README`、`docs/`、架构/模型说明、部署/排障/操作指南；
- 应用源码，按文件、类、函数或可识别符号切分并保留仓库路径与行号；
- YAML/JSON/TOML/环境变量样例等配置及其 schema；
- Dockerfile、Compose、安装和构建脚本、依赖清单；
- 测试代码、测试说明、CI workflow、模型评测或 benchmark 报告；
- Git tags、commit 元数据与可复现的文本 diff；公开 PR/Issue 只有在确属该仓库、可访问且内容许可证/条款允许时才纳入。

每个文件均进入采集清单，记录“已索引”或具体排除原因。默认不把模型权重、视频/图片大文件、完整训练集、缓存、生成物、依赖 vendor 目录、构建产物、用户数据、密钥或运行日志作为文本向量内容。它们可在获准且对问题有价值时保留文件元数据或上游链接。对图片、PDF、模型卡和数据集说明分别审核许可；只有内容允许复用、OCR/解析结果经过抽样核验且能回链到文件与页码时，才加入证据索引。

### 2.3 许可与来源审计

对代码仓库以及仓库中的第三方数据、模型、权重、图片、文档逐项识别许可和归属。每条内容记录发布方、URL、Git commit/path 或页面抓取时间、文件格式、语言、许可标识/署名要求、SHA-256、解析状态和纳入理由。

GitHub 可见或被官方指南引用不能单独证明内容可以再分发。若目标仓库没有明确许可证或许可证不允许把正文/代码打包到公开演示：

- 不把未获许可的正文和代码进入公网发布制品；
- 可保留标题、路径、commit、公开 URL 和必要的来源状态元数据；
- 报告该仓库无法作为公开语料的具体限制，并暂停公开语料构建，不用未经许可的镜像或合成内容掩盖缺口。

Seeed 中文 Wiki 的许可依据沿用仓库与页面自身声明；旧语料的许可结论不得自动套用到新的 GitHub 仓库、嵌入图片、PDF、模型或数据集。

## 3. 版本语义与检索

应用源码版本以完整 Git commit SHA 为不可变快照；上游 Git tag 作为有来源的发行标签。厂商软件栈（如 JetPack/L4T）、设备型号和语料采集时间分字段保存。不得把某个当前文档快照误称为应用最新发布版本，也不得从 `main`/`master` 字样推断设备兼容性。

RAG 支持中文问题检索中文官方资料与仓库资料中的中英文标识符、配置键、路径和代码符号。证据展示至少包含仓库、commit/tag、路径、行号或 Markdown 章节；外部厂商文档包含标题、章节/页码、版本/抓取时间及许可归属。用户筛选的 commit、标签和设备/软件基线必须限制检索范围；范围冲突或缺少基线时，展示适用性缺口，不静默混合。

BM25 保留为可解释基线；词法与稠密混合、代码符号召回、路径/依赖扩展、rerank、OCR 等作为候选策略，必须在固定的本项目留出集上比较。相似度分数只表示排序线索，不表达事实正确概率。引用必须指向当前构建中确实存在的来源位置。

## 4. 变更影响 Agent

### 4.1 输入与证据流程

Agent 优先接受此仓库的 PR/commit diff；若上游历史不可用，可接受明确标记为模拟的变更描述或仓库内两个固定 commit 之间的 diff。处理步骤：

1. 固定源仓库、基线 commit、目标 commit、差异路径和变更内容摘要；
2. 识别变更类型（模型/推理配置、相机输入、视频解码、告警规则、API/事件存储、Docker/JetPack、前端/运行参数、测试等）；
3. 从 import、调用、配置引用、Compose/CI 依赖和测试引用中提取可验证的显式关系；
4. 使用 RAG 搜索相关设计、配置、部署、排障和测试证据；语义召回只能作为待复核候选；
5. 输出受影响候选、关系类型、证据路径与版本、建议验证项、证据缺口及人工审核状态。

### 4.2 输出与责任边界

输出将“仓库显式关系”与“语义候选”分开展示，逐项包含变更来源、受影响对象、依据、置信依据/不确定性、建议验证项和需人工确认事项。没有足够证据时明确写明“资料未覆盖”或“关系待人工确认”，不猜测兼容性，不自动修改仓库、不创建 PR、不触发部署，也不替代安全负责人或工程师作最终决策。

审查过程只记录完成评测和演示所需的信息；本期不建设企业账号、RBAC、 Jira/PLM、真实签核、生产流水线或持久审计平台。

## 5. 评测与策略选择

评测题与 ground truth 绑定到目标仓库 commit、来源清单、索引/解析器和策略指纹。先盘点该仓库可用的真实 tags、commits、diff、测试和文档，再确定可构建的题集。实际 PR/Issue 不足时，使用仓库真实历史 commit diff 构建变更案例；仍不足的案例必须标为“模拟开发变更”，不可描述成上游真实工单。

题集至少覆盖：

- 文件/配置/命令/接口等精确事实查询；
- 中文自然语言与英文标识符、路径和配置键混合查询；
- 要求跨 README、源码、配置与测试的多证据问题；
- 由真实 commit diff 驱动的受影响文件与验证项发现；
- 版本/配置不明、错误 commit、冲突来源及语料外问题；
- 解析器支持的 Markdown、源代码、YAML/JSON、shell、PDF 等格式；未支持的格式单独报告，不虚报覆盖率。

检索指标包括必要证据 Recall@K、完整证据集命中率、MRR/nDCG、路径/行号正确率、版本/commit 正确率、引用支持度、无答案误答率与 P50/P95 延迟。Agent 指标包括变更类型/查询计划覆盖、已知关系召回、候选影响 precision/recall、必需测试遗漏率、无证据断言率与人工审核可用性。检索命中不等同答案正确；仓库离线评测不等同真实企业影响分析质量。

DEV 与 HOLDOUT 按文件/目录/提交分组，避免相邻 diff 或近重复问题泄漏。先冻结问题、ground truth、语料 SHA 和指标门槛，再比较 BM25、混合检索、符号/关系增强、rerank 等。不能用 HOLDOUT 逐题调参；若没有足够独立变更案例，报告样本量局限并只公布探索性结果。

## 6. 工作台与发布范围

工作台、API、来源页、示例问题、README、健康状态和 Render 构建均只显示一个活动项目及其实际来源发布者。项目页显示 GitHub 仓库与固定 commit、许可/署名状态、源文件格式覆盖、排除项、资料快照和评测指纹。不得把当前设备产品平台语料与单一应用语料合称为完整企业项目。

公网构建必须校验活动 manifest 只指向批准的单一仓库、许可字段齐全、来源哈希正确、策略与评测指纹匹配；遇到未审许可或旧领域来源时失败关闭。切换前保留当前仓库工作树中所有既有未提交/未跟踪文件；迁移后只从活动检索与发布包移出其他领域数据，不无理由删除历史评测档案。

本次用户授权只确定方案和目标；实际 GitHub 推送、合并 main 和公网部署应在实现验收后按后续指令执行，不由这份设计自动触发。

## 7. 验收条件

1. 活动索引只有一个应用仓库，以及直接解释其硬件/软件运行依赖、许可通过的官方参考资料；每条证据都能回到来源 URL、版本、路径/页码和哈希。
2. 有逐文件来源清单，完整列出目标仓库工程文件的索引状态及排除理由；第三方/官方发布者和许可证区分准确。
3. 不同 commit、release tag、设备型号与 JetPack/L4T 作为不同维度过滤，测试不会把它们混为一谈。
4. Agent 可接受真实仓库 diff 或明确模拟的 diff，检索同项目证据并输出带来源的影响候选、验证项和缺口；不写回上游。
5. 评测题、ground truth、提交/文件分组、指标定义、失败原因和语料/策略哈希可复现；真实案例与模拟案例分开统计。
6. 工作台、API、README、部署包和健康状态没有其他项目的活动入口、语料或指标。
7. 许可未知的代码/内容未进入公开制品；未完成许可证核实前不得报告公网语料迁移完成。
