# Autoware 研发变更审查与 KEP 启发式提案流程设计

## 目标

将公开演示主语料切换为 Autoware 的版本化研发资料；不将 Kubernetes KEP 文档作为 RAG 业务语料，而把 KEP 中清晰描述变更动机、范围、方案、风险、验证和决策状态的做法，吸收到现有证据约束变更审查 Agent 中。保留同一个 RAG + Agent 产品，后续可通过受版本与来源清单约束的语料配置适配面试公司的公开业务资料。完成实现与验证后，将最终版本提交到 GitHub `main` 并更新、核验当前公网演示。

## 当前状态与问题

- 当前检出的 `main` 使用 Apache DolphinScheduler 3.4.2/3.4.3 作为公开 RAG 语料；本工作区没有 Autoware 语料，也没有被公开检索清单引用的 KEP 语料。
- `PublicReviewAgent` 已能根据自然语言变更规划有限的检索子问题、调用公开 RAG、把候选证据交给模型辅助分析，并将无证据的内容保留为缺口；因此 KEP 思想应加强提案上下文和审查可读性，而不是另建一套 Agent 或替代 RAG。
- 工作区存在与本设计无关的未提交代码和未跟踪文件。实施时只修改本规格列出的相关产品资产，不覆盖、清理或提交这些既有文件。

## 用户流程

```text
自然语言变更描述 + 可选结构化上下文
  → 提案草稿（保留原文；识别变更类型、项目/语料、目标版本、影响范围；未知字段显式留空）
  → 用户确认或补充关键字段
  → Agent 形成有界检索计划并调用 RAG
  → 按版本、来源与证据 ID 整理影响候选、风险、验证建议和证据缺口
  → 人工审核：通过 / 驳回 / 暂缓
  → 可追溯地展示本次分析与审核决定
```

### 提案上下文

- 始终保留用户原始变更描述，不以摘要覆盖原文。
- 展示并允许用户修正变更类型、目标版本和影响范围；目标版本默认取所选语料清单的当前版本。
- 提案动机、目标/非目标、约束、兼容性、迁移/回滚和验证计划属于可补充信息。用户未提供时标记为“待补充/待确认”，不得由模型编造为事实；本轮只把现有输入字段和高价值缺口接入审查，不强制用户填写长表。
- 初始的确定性分类与规则查询规划保持可解释且有硬查询上限。Agent 必须继续通过现有 RAG 工具取证；证据不足时给出缺口，不得凭流程模板生成影响结论。

### 审核状态与边界

- 演示状态至少区分草稿/待分析、分析完成待审核、已通过、已驳回、暂缓；只有后续实际验证记录存在时才显示已实施/已验证。
- 每个影响候选继续绑定本次检索的有效证据 ID、版本及来源；证据范围外的模型引用必须被拒绝。
- 审核由人完成。Agent 不得批准、修改或写回 RAG 语料、公共基线或上游项目。
- 持久化只表示本演示可追溯的审查记录；不能宣称具备认证身份、企业权限控制或生产级集中审批。

## 语料与边界

- 主演示语料改为固定提交/版本的 Autoware 公开资料，优先覆盖架构/模块说明、接口或配置、版本变更记录和测试/验证资料，使跨资料影响审查有真实依据。
- 每份来源必须在清单记录仓库、固定提交或版本、路径、来源 URL、许可证/归属和内容摘要；默认只检索当前已收录版本，历史版本显式选择。
- 不下载、索引或展示 KEP 文档作为业务检索结果；可在产品/架构文档中说明流程设计“受 KEP 提案治理实践启发”，不得宣称实现 Kubernetes KEP 标准。
- 本轮只交付 Autoware 主配置和可替换语料边界，不提供任意公司切换器、多租户语料、企业私有 Git/Jira 连接器，也不声称接入任何面试公司的内部系统。
- 移除或更新 DolphinScheduler 专属的公共产品文案、硬编码过滤/引用假设及绑定其语料哈希的公开评测；无关的历史实验、合成工作流和 RAG-Challenge 数据目录不因本次任务删除。

## 架构与组件责任

- **语料构建与清单**：在 `versioned-rag-service` 中导入并固定 Autoware 来源，生成和校验检索资产；运行时仍由服务清单提供工作区、当前版本和版本过滤。
- **RAG 服务**：继续负责版本化检索、来源溯源和可选的引用约束生成；将 Apache 仓库 URL 前缀等业务特定校验改为由受信语料清单验证，不降低来源校验强度。
- **图像证据**：切换语料时重新盘点 Autoware 资料中的图/表；对与规划变更审查直接相关且含可读信息的少量图片离线 OCR、人工校核，并把文字证据绑定到原文档、图片 SHA、版本和固定提交。请求时不下载图片或调用在线视觉模型；对无可读内容的图不生成 OCR 事实。
- **变更审查 Agent**：扩展现有提案上下文/计划，不新增绕过 RAG 的自由回答路径；模型辅助输出必须受当前检索证据约束。
- **工作台**：展示提案摘要、已确认与待补充字段、检索证据/缺口、审核决定及状态；保持自然语言入口简洁。
- **评测**：为 Autoware 语料建立独立冻结问题集，包含只在相关图片中出现的事实问题；比较 BM25 与少量经审查 OCR 候选策略，测量必需来源召回、图片来源召回、版本正确性、无答案误命中、Agent 查询计划覆盖和证据引用成员校验。以冻结集选择复杂度最低且满足证据质量门槛的策略。换语料后的旧 DolphinScheduler 指标不可冒充新语料效果。

## 验收标准

1. 默认公开工作区、文案和检索证据指向 Autoware；来源全部来自清单中的固定公开版本，历史版本边界可核验。
2. 公共 RAG 清单与默认检索结果不含 Kubernetes KEP 资料；移除 KEP 语料不改变 RAG 工具调用契约。
3. 一条自然语言变更可生成保留原文的提案上下文，默认最新已收录版本；缺失的动机/约束/验证信息明确标为待补充，而不是臆造。
4. Agent 调用同一 RAG 服务；每个输出影响候选均能映射到本次返回的证据 ID，检索缺口和模型不可用状态能继续呈现。
5. 人工通过、驳回和暂缓状态可区分；任何状态都不触发公共语料或上游资料写入。
6. 新语料具有独立可复现评测；测试覆盖跨文档问题、图片中独有的可读信息、版本错配、无答案问题、缺少结构化字段和来源无效等情形；检索策略选择报告说明图片 OCR 对整体召回与无关命中的影响。
7. 更新 README 和工作台介绍时清楚区分已实现能力与未来的公司领域语料适配，不声称企业生产审批、私有系统接入或 KEP 标准兼容。

8. GitHub `main` 与已更新的公网演示均对应最终 Autoware 版本；线上 RAG 与工作台可用，并能完成一次带有效引用的变更审查。

## 不在本轮范围

- GitHub/Jira/MCP 等企业连接器、认证/ACL、跨用户审批平台和生产级审计数据库。
- 自动批准、自动修改或自动发布研发资料。
- 为每家公司维护独立代码分支、公开多个业务产品，或把私有资料发送给在线模型。
- 以模型主观回答替代冻结评测、来源许可核验或人工审核。
- 在评测和本地端到端验证未通过时发布公网，或把工作区内与本任务无关的改动一并提交。

## 集成与发布

- 实现过程中只暂存本任务文件；现有工作区改动逐项核对，未获确认的无关变更不得混入发布提交。
- 发布前运行 RAG、Agent、工作台和新语料评测；验证目标分支包含预期实现后再推送/合并至 `main`。
- 更新与 `main` 绑定的公网演示；检查公开 RAG 工作区和健康状态，至少完成一次 Autoware 检索及一次证据绑定的变更审查端到端验证。
- 向用户提供已验证的公网演示链接和对应 GitHub `main` 提交；如果部署平台未自动刷新或健康检查失败，报告具体阻塞，不宣称发布成功。

## 规格自审

- 语料替换、检索来源契约、Agent 输入/输出和人工审核边界均有明确责任与验收条件。
- Autoware 来源及版本数须在实现阶段根据上游公开仓库、许可和可稳定获取的历史版本核验；不预设未验证的语料规模或检索指标。
- 不将当前工作区的未提交文件视为本任务内容，也不清理未跟踪的实验目录。
